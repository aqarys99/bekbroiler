# 03. Медиатека и сжатие фото

## Цель
Сотрудник (owner или editor) загружает фото с телефона или компьютера. Браузер уменьшает их перед отправкой, сервер чистит EXIF/GPS и делает три размера в WebP и JPEG. Все файлы видны в разделе «Медиатека»: поиск, alt-текст, «где используется», удаление (используемый файл удалить нельзя). Окно «выбрать из медиатеки / загрузить» готово для фич 04, 06, 09, 10.

## Входит / не входит
- Входит:
  - миграция `004_media.sql` (таблица `media`);
  - загрузчик: несколько файлов в одной очереди, отправка строго по одному, прогресс по каждому файлу, сжатие в браузере (canvas);
  - серверный конвейер (ARCHITECTURE §6.1): `finfo`, белый список, лимит размера, лимит пикселей (защита от decompression bomb), поворот по EXIF, удаление EXIF/GPS (перекодирование), варианты thumb/medium/large в WebP и JPEG, случайные имена в `uploads/images/ГГГГ/ММ/`, оригинал не хранится;
  - экран «Медиатека» (сетка, очередь загрузки, фильтр по типу, поиск, постраничный вывод, «Занято X из Y») и карточка файла (просмотр, размеры, alt, «где используется», удаление);
  - реестр использований `Media::usages()`: расширяемый, каждая следующая фича регистрирует своего «потребителя»;
  - сервис места на диске `DiskUsage` (I-16, им потом пользуется дашборд 08);
  - переиспользуемый компонент «Выбрать из медиатеки / загрузить» (модальное окно, режимы «одно фото» и «несколько фото»);
  - хелперы вывода `media_url()`, `media_picture()`, `format_bytes()`;
  - пункт меню «Медиатека» (owner и editor);
  - **долг из 02:** мобильное меню-гамбургер (ширина < 900px).
- Не входит:
  - альбомы и массовая загрузка в альбом — 06 (используют загрузчик из 03);
  - загрузка документов PDF/DOCX/XLSX (`type=file`) — 05;
  - загрузка видео MP4 (`type=video`) — 07;
  - настройка «хранить оригиналы» и изменение лимитов в интерфейсе — 10 (сейчас только `config.php`);
  - поле alt на казахском в интерфейсе — 13 (колонка `alt_kk` создаётся сейчас);
  - блок «Место на диске» на главной админки — 08 (сервис готов в 03);
  - потребители в реестре (новости, альбомы, документы, педагоги, настройки) — 04, 05, 06, 09, 10.

## Изменения БД
Новый файл `migrations/004_media.sql`:

```sql
CREATE TABLE media (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  type          TEXT    NOT NULL CHECK (type IN ('image','video','file')),
  original_name TEXT    NOT NULL,              -- имя файла у пользователя, обрезано до 255 символов, без пути
  path          TEXT    NOT NULL UNIQUE,       -- база без суффикса: 'images/2026/11/<32 hex>'
  mime          TEXT    NOT NULL,              -- mime основного файла: для фото 'image/webp' (вариант large)
  size          INTEGER NOT NULL DEFAULT 0,    -- сумма байтов всех файлов на диске (6 вариантов для фото)
  source_size   INTEGER NOT NULL DEFAULT 0,    -- байты, которые пришли на сервер (после сжатия в браузере)
  width         INTEGER NULL,                  -- размеры варианта large
  height        INTEGER NULL,
  variants      TEXT    NOT NULL DEFAULT '{}', -- JSON, см. ниже
  alt           TEXT    NOT NULL DEFAULT '',   -- RU, до 300 символов
  alt_kk        TEXT    NOT NULL DEFAULT '',   -- ҚАЗ, интерфейс в фиче 13
  status        TEXT    NOT NULL DEFAULT 'ready' CHECK (status IN ('ready','processing','failed')),
  uploaded_by   INTEGER NULL REFERENCES users(id) ON DELETE SET NULL,
  created_at    TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%d %H:%M:%S','now')),
  updated_at    TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%d %H:%M:%S','now'))
);
CREATE INDEX idx_media_type_created ON media (type, created_at);
CREATE INDEX idx_media_name ON media (original_name COLLATE NOCASE);
```

Формат `variants` для фото:
```json
{"thumb":  {"w":400,"h":300,"webp":"images/2026/11/<hex>-thumb.webp","jpg":"images/2026/11/<hex>-thumb.jpg","webp_bytes":18234,"jpg_bytes":24100},
 "medium": {"w":1200,"h":900, ...},
 "large":  {"w":1920,"h":1440, ...}}
```
- Пути в `path`/`variants` — относительно `public/uploads/`. Абсолютных путей и `..` в БД нет.
- В фиче 03 строки создаются только с `type='image'`, `status='ready'` (обработка синхронная; при сбое строка не создаётся). Значения `video`/`file`/`processing`/`failed` заложены под 05 и 07.
- Будущие таблицы-потребители (`news.cover_media_id`, `album_media.media_id` и т. д.) ссылаются на `media(id)` с `ON DELETE RESTRICT` — это вторая защита к I-02.

## Серверный конвейер фото (`App\Core\ImageProcessor`, `App\Core\Uploader`)
1. Если `CONTENT_LENGTH` > `post_max_size` → 413 `too_large` **до** проверки CSRF (иначе PHP отдаёт пустые `$_POST/$_FILES` и получился бы ложный 400).
2. Нет файла или `UPLOAD_ERR_*` ≠ OK → 422 `no_file`; `UPLOAD_ERR_INI_SIZE/FORM_SIZE` или размер > лимита → 413 `too_large`.
3. Тип только по `finfo` (расширение и mime от браузера не учитываются). Белый список: `image/jpeg`, `image/png`, `image/webp`, `image/gif`. `image/heic`/`image/heif` → дальше только если есть Imagick и `Imagick::queryFormats('HEIC')` не пуст, иначе 415 `heic_unsupported`. Всё остальное, включая SVG, → 415 `not_image`.
4. `getimagesize()` (читается только заголовок). Нет размеров → 422 `broken`. `w*h > media.max_pixels` → 422 `too_many_pixels`. Дополнительно: если оценка памяти `w*h*5*1.8` больше свободной до `memory_limit` → 422 `too_many_pixels`.
5. Декодирование: GD (основной); Imagick — если нет GD или для HEIC. GIF: берётся первый кадр, анимация не сохраняется.
6. Поворот по EXIF Orientation (значения 1–8, включая зеркальные) для JPEG (и HEIC через Imagick). Если нет расширения `exif`, Orientation читается встроенным разборщиком APP1 (`ImageProcessor::readOrientation()`).
7. Варианты: длинная сторона ≤ 400 / 1200 / 1920, пропорции сохраняются, **без увеличения** (маленькое фото — все три варианта в исходном размере). Каждый вариант — WebP (`webp_quality`, прозрачность сохраняется) и JPEG (`jpeg_quality`, прозрачность заливается белым, progressive).
8. Метаданные удаляются: GD не переносит EXIF/XMP/ICC при перекодировании; Imagick — `stripImage()`. Ни в одном из 6 файлов нет EXIF, GPS, XMP.
9. Имена: `bin2hex(random_bytes(16))`, папка `public/uploads/images/ГГГГ/ММ/` по дате загрузки (создаётся с правами 0755, файлы 0644). Сначала пишутся во временные `*.tmp` и переименовываются; при любой ошибке все уже записанные файлы удаляются. Ошибка записи (нет места) → 507 `disk_full`.
10. Запись строки `media` в транзакции; если вставка упала — файлы удаляются. Временный файл загрузки PHP не сохраняется, оригинал не хранится.
11. `audit_log`: `media.upload`, `media.update` (alt), `media.delete`, `entity='media'`.

## Сжатие в браузере (`public/assets/admin/media-upload.js`)
- Файлы обрабатываются строго по очереди: сжать → отправить (XHR, `upload.onprogress`) → следующий. Без ограничения числа файлов в очереди (50 штук подряд должны проходить).
- До сжатия: тип по `file.type` и расширению. Явно не картинка (pdf, docx, mp4 и т. п.) → строка с ошибкой `not_image`, на сервер не отправляется.
- JPEG и HEIC, который браузер может декодировать (`createImageBitmap(file, {imageOrientation:'from-image'})`, запасной вариант — `<img>`): canvas, длинная сторона ≤ `client_max_side`, `toBlob('image/jpeg', client_quality)`. Ориентация применяется браузером, canvas не переносит EXIF.
- PNG и WebP: если длинная сторона > `client_max_side` — canvas с уменьшением в тот же формат (прозрачность сохраняется); иначе отправка как есть.
- GIF — отправка как есть.
- Если результат сжатия больше исходного файла — отправляется исходный.
- HEIC, который браузер декодировать не может, отправляется как есть; сервер отвечает 415 `heic_unsupported` (или обрабатывает через Imagick).
- После сжатия размер > `data-max-bytes` → ошибка `too_large` без отправки.
- Пока в очереди есть незавершённые файлы — `beforeunload` предупреждает об уходе со страницы.
- Скрипт без инлайнового JS: настройки берутся из `data-*` атрибутов (лимит, сторона, качество, URL, CSRF).

## Реестр использований (I-02, I-25)
- Интерфейс `App\Media\UsageProvider`: `key(): string` (напр. `news`), `find(array $mediaIds): array` → `[media_id => [['label' => 'Новость «Осенний утренник»', 'url' => '/admin/news/5/edit'], ...]]`. Один SQL-запрос на всех `$mediaIds` (без N+1).
- Список провайдеров — файл `app/media_usages.php` (по образцу `app/admin_menu.php`), возвращает массив имён классов. В 03 он пустой, кроме тестового провайдера: при `APP_ENV=testing` подключается `App\Media\TestUsageProvider`, который читает `storage/test_media_usages.json` (заполняется маршрутом `/__test/media-usage`).
- `Media::usages(int $id): array` — плоский список `{source, label, url}` из всех провайдеров.
- `Media::usageCounts(array $ids): array<int,int>` — для значка «Используется» в сетке.
- `Media::delete(int $id)`: под `BEGIN IMMEDIATE` перечитывает `usages()`; не пусто → `MediaInUseException` со списком; иначе удаляет строку, после коммита — все файлы из `variants`. Нарушение FK (`SQLITE_CONSTRAINT`) от будущих таблиц обрабатывается так же, как «используется».
- Отсутствующий на диске файл варианта при удалении не ошибка (удаляется только строка, предупреждение в лог).

## Место на диске (I-16)
- `App\Core\DiskUsage::summary(): array{used:int, total:?int, files:int}`: `used` = `SUM(media.size)` (без обхода папок), `files` = `COUNT(*)`, `total` — см. `disk_quota_mb`.
- Показывается на экране медиатеки строкой `media-disk-usage`; в фиче 08 тот же сервис выводится на главной.

## Хелперы
- `media_url(array $media, string $size = 'medium', string $format = 'webp'): string` — URL варианта (`/uploads/...` с учётом `base_path`).
- `media_picture(?array $media, string $size, array $attrs = []): string` — `<picture>` с `<source type="image/webp" srcset="thumb 400w, medium 1200w, large 1920w">` + `<img src=jpg loading="lazy" width height alt>`; alt — из `media.alt`, экранирован. `null` (файл удалён) → пустая строка, без битой картинки.
- `format_bytes(int $b): string` — по-русски, основание 1024, одна цифра после запятой для МБ/ГБ: `9,8 МБ`, `312 КБ`, `0 Б`.

## Критерии приёмки
- [ ] Миграция `004_media.sql` применяется на сайте после фичи 02 при первом запросе ровно один раз (I-17).
- [ ] JPEG 4000×3000, ~10 МБ, с EXIF Orientation=6 и GPS, загруженный через интерфейс: в `media` 1 строка, на диске ровно 6 файлов `<32 hex>-{thumb,medium,large}.{webp,jpg}` в `uploads/images/ГГГГ/ММ/` текущего месяца; large 1920×1440 → после поворота 1440×1920 (портрет); medium длинная сторона 1200; thumb 400; large WebP ≤ 400 КБ; thumb WebP ≤ 40 КБ.
- [ ] Ни в одном из 6 файлов нет EXIF/GPS/XMP (`exif_read_data` не находит `GPSLatitude`; в байтах нет `Exif\0\0` и `http://ns.adobe.com/xap`).
- [ ] Тот же JPEG, отправленный напрямую на сервер (без сжатия в браузере, через `request` в тесте), обрабатывается так же; фото с Orientation 3, 6, 8 показываются правильно повёрнутыми.
- [ ] Сжатие в браузере: JPEG 4000×3000 уходит на сервер с длинной стороной ≤ 2560 (проверка `source_size` и логов запроса: тело < исходного файла).
- [ ] PNG с прозрачностью: WebP-варианты сохраняют альфа-канал, JPEG — белый фон. Анимированный GIF → статичные варианты первого кадра.
- [ ] Отклоняются с кодом и текстом из «Тексты интерфейса», без записи в БД и без файлов на диске: PHP-файл с расширением `.jpg` (415), SVG (415), PDF (415, и в браузере до отправки), файл > лимита (413), PNG с заголовком 30000×30000 (422 `too_many_pixels`, не декодируется, память процесса < 64 МБ), обрезанный JPEG (422), HEIC без Imagick-HEIC (415 `heic_unsupported`), тело больше `post_max_size` (413, а не 400).

## Вопросы
1. **alt на казахском.** Колонка `alt_kk` создаётся, поле в интерфейсе — в фиче 13 (как переключатель ҚАЗ в 02). По умолчанию: так.
2. **«из Y» в месте на диске.** Хостинг не всегда отдаёт объём тарифа. По умолчанию: `disk_quota_mb` из конфига, иначе `disk_total_space()`, иначе только «Занято X».
3. **«Хранить оригиналы» (ARCHITECTURE §6.1).** По умолчанию не храним; настройка — в фиче 10.
4. **Может ли editor удалять чужие файлы?** ARCHITECTURE ограничений не задаёт. По умолчанию: да, любой свободный файл; всё пишется в журнал.
5. **Фильтр «Видео/Документы» в 03 всегда пуст.** Оставляем: фильтр работает, данные появятся в 05 и 07. Альтернатива — показывать только типы, которые есть в базе.
6. **Лимит 20 МБ.** После сжатия в браузере фото весит 0,5–3 МБ; 20 МБ нужно для HEIC/PNG без сжатия. По умолчанию 20 МБ (с учётом ini-лимитов хостинга).
